# 본문 후보 다양성과 자리별 교체

2026-10-29 사용자 피드백: 표지·목차 이후 후보가 비슷하고, 마음에 들지 않는 후보 하나만 버린 자리에 새 후보를 받고 싶다.

## 확인한 원인

- 데모는 대부분 본문에서 같은 배열의 첫 세 개(header-boxes, arrow-flow, funnel)를 선택했다. 원인 좁히기와 단계 흐름 모두 흐름형이어서 시각적 차이가 제한됐다.
- 기존 단일 재생성은 남겨둘 두 후보만 제외했다. 버린 후보 자체는 허용되어 다시 같은 레이아웃이 나올 수 있었다.
- 후보 하나를 만드는 동안에도 본문 카드 세 개를 모두 로딩 화면으로 가렸다.

## 변경

- `candidate-plan.ts`: 섹션 역할을 우선하고 필요 시 키메시지·내용 힌트로 추천한다. 현황/문제/원인/대안/실행/결론별 우선 구조를 달리한다. 같은 흐름형인 화살표·깔때기는 초기 세 후보에 함께 넣지 않는다.
- 컨설팅에 c-split-insight(통찰+근거), c-matrix(정성적 2×2 프레임), c-timeline(실행 로드맵)을 추가했다. 기존 8개를 유지해 컨설팅 11개·마케팅 6개다. Zod·데모 예시·직접 텍스트 편집·SVG 미리보기·편집 가능한 PPTX를 같은 스키마/좌표로 연결한다. 세로 타임라인 선도 SVG/PPTX에 동일한 높이를 적용한다.
- API에도 슬롯별 layoutId와 전달 목적을 명시한다. 모델이 지정 구조/순서를 따르지 않으면 기존 형식 검증 재시도 예산 안에서 수정한다. 해당 요청에 쓸 구조의 예시만 보내며 전체 템플릿을 모두 전송하지 않는다. 구성의 차이를 위해 없는 수치·근거를 생성하지 않도록 지시한다.
- 카드에 전달 목적과 ‘새 후보로 교체’를 표시한다. 단일 교체는 지금 보이는 세 레이아웃(버릴 것 포함)을 제외한다. 유사한 흐름 계열도 피한다. 표지는 표지 형식을 유지하되 현재 세 후보의 문구/데이터 지문과 같은 것은 거부한다.
- 후보 교체 API는 새 카드 1개만 생성한다. 데모도 1개만 만든다. 성공 전까지 저장된 기존 후보는 유지한다. UI는 대상 카드만 로딩 처리하고 나머지 카드를 그대로 보여준다.
- 교체한 카드가 선택된 카드라면 그 장의 선택/수정만 해제한다. 다른 카드가 선택되어 있으면 그 선택·수정은 보존한다. 수정 중인 선택 후보 교체 전에는 기존 확인을 유지한다. 요청 실패 시 기존 후보를 유지하고 같은 슬롯을 재시도한다.
- 생성 회차를 덱에 저장해 새 요청마다 추천 순서를 순환한다. 컨설팅 본문의 ‘전체 다시 생성’은 현재 세 구성을 제외한 세 구조를 만든다. 템플릿이 유한하므로 예전에 버린 형식을 영구 금지하지는 않으며 여러 회차 뒤에는 다시 등장할 수 있다.

## 기존 저장 덱

사용자가 고른 기존 후보를 자동 삭제·변경하지 않는다. 기존 덱은 본문 장을 열어 ‘전체 다시 생성’ 또는 각 카드의 ‘새 후보로 교체’를 눌러 새 기준을 적용한다. 원문 자료나 API 키는 변경하지 않는다.

## 검증

- 테스트 27개 통과: 섹션별 서로 다른 조합, 단일 자리 10회 교체, 남은 후보·선택·직접 수정 보존, 선택 후보 교체 해제, 표지 중복 방지, 잘못된 API 구조 재시도, API 교체 1개 반환, 신규 도형 범위·텍스트 넘침, 전체 17개 PPTX 네이티브 텍스트·도형 내보내기 등.
- 브라우저 데모에서 3번 현황 장표의 B만 ‘통찰+근거’로 교체했다. A/C의 DOM 내용이 이전과 동일하고 A의 선택이 유지되는 것을 확인했다. 유료 API는 호출하지 않았다.
- 대체 응답 검증은 실제 모델 출력의 논리·품질 검증과 구별한다. 실제 Luna 응답은 크레딧 확보 후 확인한다. 배포·결제는 하지 않는다.

최종 Next.js 프로덕션 빌드·TypeScript 검사도 통과했다. 개발 서버를 다시 실행했다.
