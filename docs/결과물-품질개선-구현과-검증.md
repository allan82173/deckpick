# DeckPick 결과물 품질 개선 구현·검증

2026-11-06. 기존 웹 앱의 생성 흐름을 확장한 작업 기록이다. 검증 자료와 결과는 `web/output/quality-pipeline/`에 보관한다.

## 작업 전 확인과 수정 계획

기존 생성은 `web/src/lib/ai.ts`의 목차 생성과 장별 후보 생성으로 나뉘어 있었다. API 진입점은 `web/src/app/api/[...action]/route.ts`, 전체 초안의 순차 생성과 저장은 `web/src/components/studio.tsx`가 맡았다. 웹 검색은 선택적으로 실행됐고, 첨부 발췌는 단일 질의로 골랐다. 응답 형식·허용 URL·후보 중복을 검사했으나 내용 밀도와 계획형 제목을 검사하는 과정은 없었다. 최초 장 수 선택과 대화의 장 수 해석에 12장 제한이 남아 있었다.

레이아웃은 `model.ts`, `visual-model.ts`, `candidate-plan.ts`에 정의돼 있으며, 공통 `scene.ts`의 텍스트·도형 노드를 미리보기와 `export.ts`의 PPTX 내보내기가 함께 사용한다. 이 구조를 확장해 편집·첨부·장별 대화·후보 교체 경로를 유지하기로 했다. 코드 수정 전에 이 내용을 대화로 보고했다.

`MIN_BODY_FILL`은 레이아웃별 상수다. 채움 비율은 본문 텍스트 상자 안의 추정 글자 면적을 기준으로 계산하며 전체 슬라이드 픽셀 점유율로 표현하지 않는다. 표지·목차의 구성과 근거 예외를 구분하고, 근거 예외가 있어도 계획형 제목은 검사한다.

품질 수정 횟수와 JSON 형식 재시도는 구분된다. 품질 수정은 장마다 최대 2회이며, 각 모델 응답의 형식 검증 재시도는 기존의 최대 2회를 유지한다. 수정 중 오류가 나면 마지막으로 유효했던 장을 보존한다.

계산 카드가 입력칸만 반환하는 경우에는 내부 전제의 객실 수·연수가 각각 하나로 명확할 때만 코드로 기준 수용량을 계산해 보완한다. 1년=365일 단순화 가정을 붙이고 판매량·가동률·매출 예측으로 해석하지 않는다고 표시한다. 이 보완은 별도 모델 호출을 사용하지 않는다. 내부 수량이나 기간이 모호하면 자동 계산하지 않는다.

## 출처와 기존 기능

- 각 장 하단의 `[1][3]` 표시와 발표자 노트의 근거 구분·제목·URL·확인일을 공통 장면과 PPTX에 보존한다. 이번 결과물은 표지 예외를 제외한 15장에 근거 확인일 노트가 들어 있다.
- 기존 원본 데이터와 저장 덱은 새 메타데이터가 없어도 읽을 수 있다. 이미 저장된 21~30장 덱은 읽기·편집·PPTX 내보내기를 허용하며 새 구성·페이지 추가의 상한은 20장이다.
- 새로 추가한 장에 역할이 없으면 같은 모델로 해당 장의 역할과 기존 근거 ID를 먼저 선택한다. 후속 첨부 자료의 내용은 장별 발췌 경로로 계속 전달된다. 후속 파일에서 새로 발견한 사실을 덱 전체 근거표에 자동 병합하는 기능은 추가 검증이 필요하다.
- 직접 편집, 후보 교체, 사진·문서 첨부, 장별 대화, 네이티브 PPTX 관련 기존 테스트를 함께 실행했다. 색 선택과 테마 토큰의 변경은 이번 작업에 포함하지 않았다.
- 공개 Vercel은 소개·고정 예시 정책을 유지한다. 이번 구현과 실제 API 검증은 로컬 코드에서 진행했다.

## 실제 MGRV 검증 조건

입력은 이 세션에서 확인한 MGRV × BIT 과제와 원본 Kick-off PDF를 기반으로 재구성했다. 사용자가 이번 요청의 테스트 입력 자리에 과제 프롬프트 전문을 새로 붙이지 않았으므로 완전히 동일한 원문 프롬프트 비교라고 주장하지 않는다. 주제는 MGRV × BIT 중간발표 마케팅 전략, 목적은 타깃 우선순위와 반증 조건 및 탐색 경로→채널·메시지→공실 계획의 연결, 장 수는 16장, 유형은 마케팅, 테마는 기존 ICT 숲녹색이다. 내부 검토용·마지막 출처 장을 켰다.

원본 PDF에서 목표·조건·운영을 균형 발췌했다. 실제 조사 입력은 약 5,778토큰, 27개 구간 중 12개 구간이었다. 전체 원문을 모델이 모두 검토했다고 표현하지 않는다. 과거 앱 결과인 Downloads의 `MGRV 마케팅 전략 수립.pptx`는 비교 기준으로만 읽었다.

선택 모델은 모든 단계에서 `gpt-6-luna`였다. 조사·스토리라인·장별 생성·수정은 모두 같은 모델로 실행했다. 검색을 포함한 실제 API 호출이 있었다. 최초 실행에서 드러난 응답 스키마 호환, 자료 발췌 누락, 글자 수 제약 전달 문제를 수정한 뒤 실패 지점부터 이어서 검증했다. 중간 결과도 검증 폴더에 보존했다.

공개 검색은 실행됐지만 실제 덱에 반영된 공개 근거가 1건으로 적다. 학기 일정·다른 공급자 조건·세그먼트 규모가 충분히 반영되지 않아 ICT 참고 덱 수준의 조사 깊이를 달성했다고 평가하지 않는다. 사용자가 제공하지 않은 인터뷰·견적·예약·점유 자료는 여전히 미확보다. 다음 품질 확인에서는 공개 조사 추출의 누락과 타깃별 구체성을 우선 확인해야 한다.

## 검증 파일과 재실행

- `web/tests/quality-pipeline.test.ts`에 공개 검색 조건 배제, 균형 발췌, 스키마 URL 호환, 계산 예시, 검색 불가 표시, 16장 구성, 내용 검사, 최대 2회 수정, 편집 가능한 새 구조 내보내기를 검사하는 회귀 테스트를 추가했다.
- `web/tests/run-quality-evaluation.tsx`는 실제 같은 모델의 파이프라인을 실행하고 중간 덱을 저장한다. 재실행 시 완료된 장을 이어 사용한다. 원본 PDF 경로는 사용자 Downloads에서 확인한다.
- `web/output/quality-pipeline/deck.json`에 실제 생성 데이터·근거·경고가 있다. `inspection.json`, `preview.html`, `montage.jpg`, `slide-01.png`~`slide-16.png`와 편집 가능한 검증 PPTX를 함께 저장했다. 이 폴더는 공개 배포 제외다.
- 브라우저에서 `/new`의 공개 검색 주제·출처 장·내부 검토용 옵션과 20장 선택을 확인했다. 좁은 화면에서 새 옵션이 한 줄로 압축되는 문제를 수정하고 다시 확인했다.

최종 코드에서 80개 테스트, TypeScript 검사와 배포용 빌드가 모두 통과했다.

이미지 검수 결과는 모든 16장을 렌더링해 확인했고 텍스트 넘침과 폰트 대체는 없으며, 동일 형식 연속 3장은 없고, 2·4장의 낮은 채움 비율은 경고로 남겼다.
