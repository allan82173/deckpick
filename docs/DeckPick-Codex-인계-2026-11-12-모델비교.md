## 1. 목표

- **최종 목표:** 12월 인턴 지원 전까지 DeckPick을 "만들고 → 실제 사용자로 검증하고 → 숫자로 개선한" 포트폴리오 케이스로 완성한다. 실행 계획은 Claude Docs 문서 "DeckPick 포트폴리오화 실행 계획"에 있다.
- **이번 작업의 목표:** 싼 모델 두 개, GPT `gpt-6-luna`와 Claude `claude-haiku-5-5`가 **같은 수준 이상의 덱**을 내게 만든다. 출력이 똑같을 수는 없으니, 같은 채점표에서 같은 점수가 나오는 것을 목표로 한다.
- **원칙:** 모델별 차이는 지시문보다 **코드 검사·보정**으로 막는다. 모델이 지시를 어떻게 받아들이든 결과물을 코드가 고치면 결과가 같아진다.

## 3. 다음 할 일 (순서대로)

### 3-1. 비교 자료 정리
- 사용자가 주는 Luna·Haiku 결과(각 PPTX + 실행 리포트 md/json)를 `web/output/model-compare/2026-11-12/{luna,haiku}/`에 둔다. 원본은 덮어쓰지 않는다.
- 두 실행의 조건(주제·유형·단계·장 수)이 같은지 먼저 확인한다. 다르면 사용자에게 알린다.

### 3-2. 블라인드 품질 평가
- 어느 모델인지 가린 채(덱 A·B) 같은 채점표로 장마다 평가한다. 가능하면 평가를 별도 에이전트(서브 에이전트)에 맡겨, 지시문을 고친 쪽이 자기 결과를 채점하지 않게 한다.
- 채점표:
  1. 키메시지가 주제에 대한 주장인가(덱 메타·판단 보류·계획형 아님)
  2. 본문이 키메시지를 뒷받침하고 근거 ID가 맞게 연결됐나
  3. 레이아웃 깨짐(겹침·넘침·과도한 빈 공간)
  4. 본문에 `[추론]` 같은 표시나 근거 번호가 남았나
  5. 덱 흐름(결론 요약 → 근거 → 판단 → 다음 행동)
  6. 실무에서 그대로 쓸 수 있는 장 수
- 리포트에서 비용(토큰×단가+검색), 소요 시간, 단계별 호출 수, 재시도 수, 장표 경고 수를 표로 같이 뽑는다.

### 3-3. 차이를 코드 규칙으로 옮기기
Luna가 나은 항목마다 원인을 찾아 **코드 검사·보정**으로 막고, 테스트에 실제 문장·데이터를 넣는다. 이미 보이는 후보는 다음과 같다.
- **Haiku 재시도 감소:** 후보 45회·형식 보정 15회의 원인이 된 검증 실패 유형을 리포트 `warnings`·실패 사유에서 집계해, 자주 걸리는 규칙부터 코드 보정으로 바꾼다.
- **단계별 모델 설정(선택):** 판단·장별 설계 2회만 상위 모델로 돌리는 설정. 덱당 약 +$0.2이며, 사용자 승인 후 진행한다.
- **후보 단계 캐시:** 배포판 Sonnet 실행에서 후보 캐시 적중이 5%였다. 동시 요청이 캐시 생성 전에 나간 탓으로 보이니, 첫 장을 먼저 보내고 나머지를 보내는 방식을 검토한다.
- **'설문 결과' 형식 오선택:** 근거에 표본 수·기간이 없으면 survey-findings 형식을 후보에서 뺀다. 11-09 20장 실행에서 빈 장이 생긴 원인이다.
- **여러 탭 저장 충돌:** 작업 중인 덱이 localStorage의 한 칸(`deckpick-deck`)에 저장돼, 탭 두 개면 마지막 저장만 남는다. 덱 ID별로 저장하도록 고친다(테스터 대비).

### 3-4. 검증과 기록
- 변경마다 `npm run typecheck`, `npm test`, `npm run build`를 돌린다. 노트북에서는 `web/output/claude-sync/verify-build-restart.cmd`가 세 단계와 서버 재시작을 한 번에 한다.
- 유료 실행은 예산(예상 토큰·금액)을 먼저 보고하고 사용자 승인을 받는다. 비교 실험은 별도 승인이 필요하다. 실패 기록도 지우지 않는다.
- 끝나면 `docs/DeckPick-3차-안정화-진행.md`에 바꾼 파일과 이유, 검사 결과, 남은 일을 남기고 GitHub에 push한다(Vercel 자동 배포).
