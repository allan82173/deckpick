# Snapdeck 비교와 ICT 표현 확장 검토

검토: 2026-10-29. 사용자 요청으로 Google 로그인 후 Snapdeck 실제 화면을 확인하고 Kixx 주제의 5장 샘플을 생성했다. 앱 코드나 기존 사용자 덱은 이번 비교 작업에서 수정하지 않았다.

## 확인한 샘플과 범위

- URL: https://www.snapdeck.app/project/01a1866e-a3b5-7951-b3da-4c337a262456
- 설정: Piece of Cake 1.1, Report, Greenery, PPT 16:9, 5장. 모델·스타일별 전수 비교가 아닌 단일 샘플이다.
- 공개 브랜드 주제와 검토 질문만 입력했다. 과거 산학 원본 파일, 수치, 설문·인터뷰 결과는 Snapdeck에 업로드하지 않았다. 미제공 근거는 확인 필요·가설로 표시하도록 요청했다.
- 초안의 시각화 계획에서 Step Process Diagram / Data Table / Flowchart를 구분하고 수정할 수 있었다.
- 실제 생성 결과와 내려받은 PDF 5장을 검토했다. PDF는 참고자료/Snapdeck-Kixx-비교/Kixx-Snapdeck.pdf에 있다.
- 편집기에서 텍스트, 이미지, 아이콘, 도형, 그래프, 현재 장 재생성, 배경의 단색·선형·원형 설정을 확인했다. Graph 메뉴에 CSV·Excel·Google Sheets 입력이 있었다. 해당 가져오기·연동을 실행하거나 정확성을 검증한 것은 아니다.
- 내보내기에는 PDF·PNG·Figma·PPTX가 표시됐으나 이 계정에서 당시 Figma·PPTX는 비활성화였다. 전체 제품의 미지원이나 모든 유료 플랜의 제한이라고 일반화하지 않는다.
- 새 결제·플랜 변경·공유·공개 게시를 수행하지 않았다. 기존 크레딧으로 사용자가 허용한 샘플 1건을 실행했다. 정확한 차감량은 확인하지 않았다.

## 실제 결과의 장점과 한계

Snapdeck은 기획 내용과 시각화 종류를 초안에서 함께 결정하고, 생성 후 개별 요소를 편집하는 도구가 있다. 테마와 용도 스타일을 구분하며 Report·Standard·Presentation·Keynote·Portfolio·Proposal을 선택할 수 있었다. 화면에 큰 템플릿 라이브러리도 제공한다. 내부 생성 엔진이 HTML인지, 배치가 완전 자유인지, 어떤 모델로 최종 렌더링하는지까지 확인한 것은 아니다.

Kixx 샘플은 근거 미제공 상태와 가설 표시를 유지했으며, 표와 흐름도의 구분은 됐다. 다만 PDF의 2·4·5장은 모두 좌측 설명과 우측 세로 단계의 유사 배치였다. 한 번의 기본 모델 샘플에서도 표현 반복은 남았다. 5장 제약 아래 생성 결과는 표지·검토 범위·분석 틀·여정 가설·채널 실행안이었고, 요청했던 검증 지표와 우선순위가 독립된 마지막 장으로 구성되지는 않았다. 초안·최종의 지시 이행 여부는 사람이 확인해야 한다.

## DeckPick에서 반복되는 직접 원인

코드 기준 현재 11개 컨설팅 layout ID와 6개 마케팅 layout ID가 있으며 c-cover에는 세 가지 추가 스타일이 있다. 표지·목차를 제외한 본문 구조의 수는 이보다 적다.

1. `demoOutline`의 섹션 순서와 문구가 사전 정의돼 있다. ‘목차·현황·문제·원인·결론’은 덱 유형이 아니라 데모의 기본 장 역할이다. 실제 덱 유형은 컨설팅/보고서와 마케팅/피치다.
2. `candidatePlan`은 섹션 키워드가 맞으면 본문 메시지보다 섹션 이름을 우선한다. 같은 ‘문제’라도 고객 여정 문제인지 정보 단절 문제인지에 따른 구조 선택이 약하다.
3. `slotPlan`을 서버가 먼저 지정하고 생성 모델이 그 레이아웃을 정확히 따르도록 강제한다. 모델이 새로운 연결 구조를 구상해도 렌더러에 없는 구조를 출력할 수 없다.
4. 데이터 계약이 고정돼 있다. c-arrow-flow는 2~4개 블록, c-compare는 2~3개 비교 대상, c-matrix는 네 칸이다. 역할별 6단계 흐름, 자유 위치의 포지셔닝 맵, 다층 데이터 연결 구조를 그대로 담을 수 없다.
5. 한 화면에 후보 세 개를 보여 주는 것과 전체 표현 라이브러리가 세 개인 것은 다르다. 비용을 늘려 후보를 6개 생성해도 같은 고정 구조라면 반복 문제는 남는다.

## 무엇이 추가 입력이고 무엇이 구현 책임인가

사용자가 더 주지 않아도 만들 수 있는 것: 인과·분기·고객 여정·역할별 프로세스·자유 좌표 포지셔닝·기준 대응·전후 비교·시스템 구조 같은 표현 방식, 여백과 위계, 화살표·강조·영역의 배치 규칙. 기존 스타일 자료와 이번 PDF면 출발 기준은 충분하다.

추가 근거가 필요한 것: 실제 고객 조사와 인용, 측정값·단위·기간·분모, 기업의 상대 위치와 축을 선택한 이유, 요청과 기록의 실제 연결 관계, 프로젝트의 최종 판단. 외부 공개 자료로 보완할 수 있는 정보와 프로젝트 당사자만 아는 정보를 구분한다. 형식이 필요하다는 이유로 수치나 인과를 지어내지 않는다.

## 다음 구현의 우선순위 제안

단순히 레이아웃 수만 늘리기보다 장표를 ‘역할 → 근거 종류 → 논리 관계 → 표현’으로 선택하도록 변경한다. 예: 문제라도 인용·관찰·수치·단절 관계 중 무엇을 보여 줄지 먼저 판단한다.

1. 인용→원인→가설의 세 부분, 증거 행과 시사점, 자유 위치 포지셔닝 맵을 우선 구현한다.
2. 5~6단계 역할별 흐름, 기능→요구사항 대응, 다층 시스템 구조, 사례의 전후 비교를 추가한다.
3. 차트는 기간·분모·단위·실측/추정 구분을 포함하는 수치 계약과 함께 구현한다. CSV 첨부 텍스트 발췌가 실제 차트용 정형 데이터 입력을 대신하지 않는다.
4. 전체 후보 세 개를 유지하면서 표현 방식을 사용자가 선택·교체하고, 단순 회전보다 내용 관계를 기준으로 배치를 고르게 한다.
5. 확정된 후보는 미리보기와 네이티브 PPTX가 같은 구조를 출력하도록 검증한다.

이 파일은 분석 및 구현 제안이며 위 새 본문 구조가 이미 앱에 추가됐다는 뜻은 아니다.
